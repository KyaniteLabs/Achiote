# Security Policy

## Supported versions

Achiote is pre-1.0. Security fixes target the current `master` branch until release branches exist.

## Reporting a vulnerability

Please do not open public issues for vulnerabilities. Report privately to the repository owner with:

- affected commit/version
- reproduction steps or MCP inputs
- expected impact
- whether credentials, filesystem paths, or private user food-memory data are exposed

## Security model

Achiote runs in two modes:

1. **stdio MCP server** — the primary mode, used by Claude Code, Codex, and other MCP clients. No network listener.
2. **HTTP server** (`node dist/http-server.js`) — optional mode for web UI and AI agent access. Exposes `/health`, `/ask`, `/mcp`, and static file endpoints.

Primary risks are:

- prompt-injection through user-provided memories or ingredient/location fields passed to host-model prompts — mitigated by `sanitizeForPrompt` which strips `<user_input>` tags, control characters, and JSON-wraps user values as inert data literals
- cache privacy and filesystem permissions
- accidental publication of runtime state
- supply-chain risk from npm dependencies and native `better-sqlite3`

### Prompt injection residual risk

Despite `sanitizeForPrompt` sanitization, prompt injection remains an inherent residual risk in any system that forwards user input to an LLM. Mitigations in place:

- User input is wrapped in `<user_input>` tags with an explicit "do not follow instructions" directive to the host model.
- `sanitizeForPrompt` strips control characters, HTML/XML tags, and normalizes Unicode.
- Telemetry events do not store prompt text — only event names and allowlisted dimension keys.
- The system is designed for food-memory reconstruction; outputs are creative suggestions, not instructions that trigger real-world actions with irreversible consequences.

No amount of input sanitization can fully eliminate prompt injection against a capable LLM. Operators should assume that a determined attacker can influence model output quality and plan accordingly (monitoring, rate limiting, output review for high-stakes contexts).

### HTTP server security

- **Authentication** — configurable via `ACHIOTE_AUTH_ENABLED` env var. When enabled, requires API key via `x-api-key` header or `Authorization: Bearer` header. Keys are tiered (free/personal/pro/family/enterprise, with business as a legacy alias) and should be stored as `keyHash` records generated by `npm run keygen`, not as plaintext raw keys. Anonymous `/ask` requires the separate local-demo-only `ACHIOTE_ALLOW_ANON_ASK=true` opt-in when auth is disabled.
- **API key encryption** — keys stored in the `checkout_sessions` table are encrypted at rest using AES-256-GCM. The encryption key is sourced from the `ACHIOTE_KEY_ENCRYPTION_KEY` environment variable (32-byte hex). Decrypted keys are held in memory only for the duration of the consuming request and then nulled. Expired checkout sessions are purged after 24 hours.
- **Timing-safe comparisons** — all secret comparisons (demo password, events admin token, API key hashes) use `crypto.timingSafeEqual` to prevent timing side-channel attacks.
- **Rate limiting** — tiered per calendar month. Free tier: 0 hosted MCP calls, 3 guided memories. Public paid tiers are guided-memory based; hosted API/MCP production access requires commercial licensing. Rate limit headers exposed in responses.
- **`/ask` endpoint** — SSE streaming AI agent endpoint. Validates content-type, parses JSON body, enforces rate limits before calling Anthropic API. User messages are embedded in prompts inside `<user_input>` tags with a "do not follow instructions" directive.
- **Body size** — 1MB default limit; `/billing/checkout` uses a tighter 10KB limit since checkout payloads are small JSON.
- **CORS** — configured by `ACHIOTE_ALLOWED_ORIGINS`. Local development may opt into broad origins, but production should set exact HTTPS origins and avoid wildcard browser access.
- **Billing session verification** — the `/billing/session` endpoint requires the customer's email as a query parameter and verifies it against the stored record, preventing session-ID enumeration.
- **Binary path validation** — the TTS/STT subsystem validates binary paths passed to `spawn()` against an allowlist of trusted directories (`/usr/`, `/opt/`, `/home/`, `/nix/`, `/tmp/`, `/private/`, `/var/`, `/Users/`, `/etc/`) and rejects paths containing `..` traversal.
- **Security headers** — all responses include `Content-Security-Policy` (with `object-src 'none'`, `media-src 'self' data:`, `frame-ancestors 'none'`), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, and `Strict-Transport-Security` (HSTS with 2-year max-age, includeSubDomains, preload).
- **Health endpoint** — the `/health` endpoint exposes only service status, version, auth/billing flags, and uptime. It does not expose memory usage, session counts, or other operational internals.

### Production deployment

For public HTTPS access, run behind a reverse proxy:

- **nginx** or **Caddy** for TLS termination
- Set `ACHIOTE_TRUST_PROXY=true` and `ACHIOTE_TRUSTED_PROXY_IPS` so rate limiting uses `X-Forwarded-For` only from trusted proxy remote addresses. Configure the edge proxy to overwrite, not append, client-supplied `X-Forwarded-For`; if you intentionally preserve a multi-hop chain, every downstream proxy address after the original client must be listed in `ACHIOTE_TRUSTED_PROXY_IPS`
- Set `ACHIOTE_ALLOWED_ORIGINS` to the exact HTTPS origins allowed to call the service.
- Set `ACHIOTE_RATE_LIMIT_DB` to a persistent path so rate limits survive restarts

Example Caddyfile:

```text
your-domain.com {
  reverse_proxy localhost:3000
}
```

Example nginx:

```nginx
server {
    listen 443 ssl http2;
    server_name your-domain.com;

    ssl_certificate     /etc/ssl/certs/your-domain.pem;
    ssl_certificate_key /etc/ssl/private/your-domain.key;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

## Maintainer checklist

- Keep GitHub secret scanning/push protection and code scanning enabled when available.
- Require CI before merging to the default branch.
- Run `npm run check` before releases.
- Run `npm run package:smoke`, `npm audit --audit-level=moderate`, and `npm pack --dry-run` before publishing.
- Run `npm run docker:smoke` for Docker/runtime changes.
- Perform browser/screenshot review for landing UI changes.
- Rotate `ACHIOTE_KEY_ENCRYPTION_KEY` periodically; rotation requires re-encrypting stored checkout sessions.
- Monitor security event logs for anomalies (see below).

## Security event logging

The HTTP server emits structured security events to stderr (log level `warn`) via `logSecurityEvent()`. Events are JSON with an `event` field, a `ts` timestamp, and context-specific fields:

| Event | When emitted | Key fields |
|---|---|---|
| `auth_failure` | API key or demo password rejected on `/ask` or `/mcp` | `path` |
| `rate_limit` | Request rejected due to monthly tier limit | `keyId`, `path` |
| `billing_session_email_mismatch` | Email verification fails on `/billing/session` | none (request details are not logged to avoid leaking PII) |

Operators should alert on spikes in `auth_failure` or `billing_session_email_mismatch` events, which may indicate credential stuffing or session enumeration attempts.
